What to say:
  • The system has three inbound lanes: Mirth Connect (HL7 v2), CSV batch import, and SMART app OAuth2.
  • Every inbound payload — regardless of source — passes through the same trace logging layer, producing a Trace ID and step-by-step audit record.
  • The FHIR mapper is stateless: it re-transforms from raw HL7 on demand, so the DB stays lean and transform logic evolves independently.
  • Downstream delivery happens two ways: synchronous FHIR REST API, and asynchronous webhook push to registered EHR endpoints.

2. HL7 v2 → FHIR R4 Transformation Pipeline

sequenceDiagram
    autonumber
    participant MC as Mirth Connect

/api/mirth/hl7/

hl7_utils.py
    participant MAP as FHIR Mapper
    participant X12 as X12 Generator

    MC->>API: POST raw HL7 (Authorization: Bearer JWT)
    API->>API: validate_mirth_jwt() — verify iss, aud, alg
    alt JWT invalid / missing
        API-->>MC: 401 + HL7 ACK AE (Application Error)
    end
    API->>PAR: parse MSH → message_type, trigger_event
    PAR->>PAR: route by type
ADT→A01  ORU→R01  ORM→O01  MDM→T01  SIU→S12
    PAR->>MAP: extract PID → FHIR Patient resource
    PAR->>MAP: extract PV1 → FHIR Encounter resource
    MAP->>X12: fhir_to_837_claim(patient, encounter)
    X12->>X12: generate_835_from_837() — simulate payer ERA
    X12->>X12: reconcile_837_835() — billed vs paid
    API->>DB: INSERT HL7MessageLog (steps[], trace_id, processing_status)
    API->>DB: INSERT ClaimRecord (x12_837, x12_835, balance_due)
    API-->>MC: 200 + HL7 ACK AA (Application Accept)
What to say:
  • The entry point is a JWT-authenticated webhook — every Mirth Connect channel sends a Bearer token with issuer and audience claims validated server-side.
  • Routing is done by reading MSH-9 (message type + trigger event). Each type has its own transform function: ADT produces Patient + Encounter, ORU produces DiagnosticReport + Observations.
  • The ACK response follows the HL7 v2 protocol: AA = Accept, AE = Error, AR = Reject. Mirth checks this to decide whether to retry.
  • Claim generation happens inline — 837P (professional claim) is generated from the FHIR resources, then a simulated 835 ERA is created for reconciliation demo purposes.

3. SMART on FHIR — OAuth2 Authorization Code + PKCE

sequenceDiagram
    autonumber
    participant APP as SMART App
(e.g. patient portal)
    participant WK as /.well-known/
smart-configuration
    participant AZ as /oauth2/authorize
(consent screen)
    participant TK as /oauth2/token
    participant IX as /oauth2/introspect
    participant FK as /fhir/Patient/

    APP->>WK: GET /.well-known/smart-configuration
    WK-->>APP: JSON — authorization_endpoint, token_endpoint,
scopes_supported, capabilities

    Note over APP: Generate PKCE pair
code_verifier = random(43 chars)
code_challenge = BASE64URL(SHA256(verifier))

    APP->>AZ: GET /oauth2/authorize
?client_id=XYZ&scope=launch/patient+patient/*.read
&code_challenge=ABC&code_challenge_method=S256
    AZ->>AZ: validate client · check redirect_uri
show consent screen to logged-in user
    AZ-->>APP: 302 → redirect_uri?code=AUTH_CODE&state=xyz

    APP->>TK: POST /oauth2/token
grant_type=authorization_code
code=AUTH_CODE · code_verifier=RAW_VERIFIER
    TK->>TK: verify PKCE: SHA256(verifier) == challenge
    TK-->>APP: 200 JSON
{access_token (JWT), token_type: Bearer,
patient: "10001", expires_in: 3600,
refresh_token: XYZ}

    APP->>FK: GET /fhir/Patient/10001
Authorization: Bearer <JWT>
    FK-->>APP: FHIR Patient resource

    Note over APP,IX: Resource server validates token
    APP->>IX: POST /oauth2/introspect · token=JWT
    IX-->>APP: {active:true, scope:"patient/*.read", patient:"10001"}
What to say:
  • SMART on FHIR is the OAuth2 profile for FHIR. ONC requires every certified EHR to expose /.well-known/smart-configuration so third-party apps can discover the authorization server without hardcoding URLs.
  • PKCE (Proof Key for Code Exchange) prevents authorization code interception attacks. The app generates a random code_verifier, hashes it with SHA-256 to get the code_challenge, sends only the hash to the server, then proves ownership at token exchange time by sending the original verifier.
  • The patient context field in the token response is unique to SMART — it tells the app which patient the user authorized access for, without needing a separate API call.
  • Token introspection (RFC 7662) lets resource servers validate tokens without knowing the signing secret — they just POST the token to the introspect endpoint and get back active/inactive + metadata.
  • The scope vocabulary uses a permission model: patient/Patient.read means read-only access to Patient resources for the authorized patient context; system/*.read is server-to-server access to all resources.

4. Bulk FHIR Patient/$export (Async Polling Pattern)

sequenceDiagram
    autonumber
    participant C as Client
(payer / analytics)
    participant EX as GET /fhir/Patient/$export
    participant ST as GET /fhir/bulkstatus/<job_id>/
    participant DL as GET /fhir/bulkfiles/<job_id>/Patient.ndjson

    C->>EX: GET /fhir/Patient/$export
?_type=Patient,Encounter&_since=2024-01-01
    Note over EX: Process HL7 records → build NDJSON
de-duplicate patients by MRN
    EX-->>C: 202 Accepted
Content-Location: /fhir/bulkstatus/<job_id>

    loop Poll until complete
        C->>ST: GET /fhir/bulkstatus/<job_id>
        alt Still processing
            ST-->>C: 202 + X-Progress: processing
        else Complete
            ST-->>C: 200 JSON manifest
{transactionTime, output:[{type,url,count}]}
        end
    end

    C->>DL: GET /fhir/bulkfiles/<job_id>/Patient.ndjson
    DL-->>C: application/fhir+ndjson
{"resourceType":"Patient","id":"10001",...}
{"resourceType":"Patient","id":"10002",...}
What to say:
  • Bulk FHIR (FHIR Bulk Data IG v2.0) is the standard for exporting large datasets. CMS mandates it for patient access APIs under CMS-9115-F.
  • The async polling pattern is required because exports can take minutes/hours for large datasets. The server returns 202 Accepted immediately with a Content-Location header pointing to the status endpoint.
  • NDJSON (Newline-Delimited JSON) is one FHIR resource per line — more efficient for streaming than a FHIR Bundle because processors don't need to load the whole file into memory.
  • The _since parameter enables incremental exports — clients only pull records changed after their last sync, which is critical for payer data pipelines.
  • On this Vercel deployment the export processes synchronously (serverless — no background workers). In production you'd use Celery + SQS or Azure Batch for large-scale async processing.

    style X837 fill:#cfe2ff
    style X835 fill:#d1e7dd
    style RECON fill:#fff3cd
What to say:
  • An 837P (professional claim) is the EDI transaction a provider sends to a payer. Key segments: NM1 (names), CLM (claim header with total charge), SV1 (service line with procedure code and fee).
  • The 835 ERA (Electronic Remittance Advice) is the payer's response. It maps back to claim lines and explains any payment adjustments using CARC/RARC codes (claim/remittance adjustment reason codes).
  • Reconciliation compares the billed amount on the 837 against the paid amount on the 835 and computes patient responsibility and balance due. This is a daily operational task for billing teams.
  • In production the 835 arrives via a clearinghouse (e.g. Change Healthcare, Availity). This demo simulates the payer response to show the full lifecycle without an actual payer connection.

    Note over DOC: Provider selects order: MRI knee (73721)

    DOC->>CRD: POST order-select hook

    CRD-->>DOC: CDS Card — warning
"Prior Authorization Required"

    Note over DOC,DTR: Provider collects required documentation

    DOC->>PAS: POST /api/prior-auth/pas/

clinical_notes: "...osteoarthritis..."}
    PAS->>PAS: evaluate medical necessity criteria
    alt Approved
        PAS-->>DOC: ClaimResponse Bundle
{outcome: "approved", preAuthRef: "PA-XXXX",
valid 90 days}
    else Pended
        PAS-->>DOC: ClaimResponse Bundle
{outcome: "pended",
disposition: "additional info required"}
    else Denied
        PAS-->>DOC: ClaimResponse Bundle
{outcome: "denied",
disposition: "criteria not met"}
    end
What to say:
  • Da Vinci is an HL7 FHIR Accelerator project. It defines Implementation Guides for payer-provider interoperability. CMS-0057-F (2026) mandates payers implement the Da Vinci IGs.
  • CRD (Coverage Requirements Discovery) uses the CDS Hooks standard — a REST protocol for EHRs to call decision support services at clinical workflow points (e.g. order-select, order-sign).
  • PAS (Prior Authorization Support) submits the actual PA request as a FHIR Claim resource bundle, replacing fax-based and portal-based workflows.
  • DTR (Documentation Templates and Rules) (not yet implemented here) auto-populates questionnaires from patient EHR data, reducing manual documentation burden on providers.
  • The payer responds with a FHIR ClaimResponse resource — approved includes a preAuthRef number valid for a defined period; pended means more info is needed; denied includes the reason.

7. Traceability & Audit Logging

graph TB
    subgraph "Every inbound payload"
        IN["Inbound message\n(HL7 / CSV / JSON)"] --> TID["Assign Trace ID\nuuid hex — 32 chars"]
    end

    subgraph "TraceLog record"
        TID --> LOG["TraceLog\n• trace_id\n• input_type\n• raw_payload\n• processing_status"]
    end

    subgraph "TraceStep records (per processing step)"
        LOG --> S1["Step 1: AUTH\nstatus: OK / ERROR\n{token_claims}"]
        LOG --> S2["Step 2: PARSE\nstatus: OK / WARN\n{message_type, segments_found}"]
        LOG --> S3["Step 3: VALIDATE\nstatus: OK / WARN / ERROR\n{missing_fields, assumptions}"]
        LOG --> S4["Step 4: TRANSFORM\nstatus: OK / ERROR\n{fhir_resources_created}"]
        LOG --> S5["Step 5: ACK\nstatus: OK\n{ack_code: AA/AE/AR}"]
    end

    subgraph "Operational use"
        S1 & S2 & S3 & S4 & S5 --> UI2["Trace Log UI\n/trace/logs/\nfilter by status / type / error"]
        UI2 --> INV["Post-incident investigation\n'What happened to message X?'"]
    end

    style S3 fill:#fff3cd
    style INV fill:#d1e7dd
What to say:
  • Every payload — including auth failures — gets a Trace ID before any processing begins. This ensures that even failed messages are recoverable for investigation.
  • Steps are recorded as discrete records with OK / WARN / ERROR status. WARN means the system made a controlled assumption (e.g. missing non-critical field) but continued processing. This distinction is critical operationally — it separates noise from real failures.
  • Error categories (VALIDATION, MAPPING, AUTH, FACILITY_VARIANCE, DOWNSTREAM) let operations teams route failures to the right team without reading log details.
  • The trace log answers the most common post-incident question: "We sent message X on Tuesday — did you receive it, and what happened to it?" Without a trace, this takes hours. With it, it takes seconds.

8. CMS Compliance Landscape

graph LR
    subgraph "CMS-9115-F — Interoperability Rule (2021)"
        A1["Patient Access API\nFHIR R4 + SMART on FHIR\n→ implemented: FHIR endpoints\n+ OAuth2 server"]
        A2["Provider Directory API\nFHIR R4 Endpoint"]
        A3["Payer-to-Payer Data Exchange\nBulk FHIR\n→ implemented: Patient/$export"]
    end

    subgraph "CMS-0057-F — Prior Auth Rule (2026)"
        B1["Electronic PA via FHIR\nDa Vinci PAS\n→ implemented: /api/prior-auth/pas/"]
        B2["PA Decision on EOB\nClaims-based reporting"]
        B3["Reason Codes in Denial\nStructured FHIR ClaimResponse\n→ implemented: outcome + disposition"]
    end

    subgraph "US Core IG (ONC HTI-1)"
        C1["Must Support elements\nPatient · Encounter · DiagnosticReport"]
        C2["USCDI v3 data classes\nDemographics · Problems · Meds"]
    end

    A1 & A3 -->|"requires"| C1
    B1 -->|"uses"| C1
What to say:
  • CMS-9115-F (2021) requires Medicare/Medicaid payers to expose a Patient Access API (FHIR R4 + SMART on FHIR) so patients can access their claims and clinical data via third-party apps. This is why SMART on FHIR is the most-requested capability in payer interoperability roles.
  • CMS-0057-F (2026) mandates electronic prior authorization via FHIR — payers must implement Da Vinci CRD, PAS, and DTR, and must return PA decisions within 72 hours (1 hour for urgent). It also requires PA decisions to appear on Explanation of Benefits claims.
  • US Core IG defines the minimum FHIR profile requirements for ONC-certified EHRs. It specifies which elements must be supported on each resource type — these are the "must support" flags you'd configure in a production FHIR server like HAPI.
  • An interoperability roadmap for a payer would typically sequence: Patient Access API (done) → Payer-to-Payer exchange (Bulk FHIR) → Provider Directory → Electronic PA (Da Vinci).
