1. POST /api/adt/trigger/

2. ADTTriggerView (adt/views.py)
   └─ validate via ADTTriggerSerializer
   └─ call generate_adt(patient_id, "A01")  → raw HL7 string
       MSH|^~\&|DEMO|FAC1|...|ADT^A01|...
       EVN|A01|20240315120000
       PID|1||P-001^^^...|Smith^John||19800315|M
       PV1|1|I|3W^301^A^FAC1

3. ADTMessage.objects.create(...)  →  stored in DB

4. create_dft_from_adt(msg) called automatically
   └─ generates DFT^P03 + X12 837P
   └─ DFTMessage + DFTChargeItem stored

5. Response: ADTMessageSerializer JSON (includes raw_hl7)

4 — HL7 ORU & ORM

ORU^R01 — Lab Result
SegmentsMSH · PID · PV1 · OBR · OBX
OBR-4Ordered test (LOINC code + name)
OBX-3Observation code (LOINC) — maps to FHIR Observation.code
OBX-5Observation value (result)
OBX-6Units (g/dL, %, etc.)
OBX-7Reference range
OBX-8Abnormal flag (H/L/N)
FHIR outputDiagnosticReport + Observation

Key insight: OBX-3 is always a LOINC code in a standards-compliant interface. If a sending system uses local codes, the integration engine must map them to LOINC before forwarding downstream.

ORM^O01 — Clinical Order
SegmentsMSH · PID · PV1 · ORC · OBR
ORC-1Order control (NW=new, CA=cancel, DC=discontinue)
ORC-2Placer order number (ordering system ID)
ORC-3Filler order number (fulfilling system ID)
OBR-4Universal service ID (what is ordered)
OBR-7Observation date/time (when collected)
FHIR outputServiceRequest

ORM flows from the ordering system (EHR) to the fulfilling system (Lab/Radiology). The OBR-4 code should be a LOINC or CPT code identifying the service.

Demo endpointGET /api/adt/dft/
Code fileadt/dft_generator.py, adt/dft_service.py
FT1 → X12 837P Mapping
HL7 FT1 Segment          →   X12 837P Segment

FT1-4  (service date)    →   DTP*472*D8*YYYYMMDD~
FT1-16 (procedure code)  →   SV1*HC:{CPT-code}*...
FT1-11 (unit amount)     →   SV1 element 02 (charge amount)
FT1-10 (quantity)        →   SV1 element 04 (service units)
FT1-1  (line number)     →   LX*{line}~ (service line counter)

Sum of all FT1-11 × FT1-10  →  CLM02 (total billed amount)

One DFT message = one CLM loop in the 837P
Each FT1 segment = one LX/SV1 service line

Admission charges (A01):    Room/Board, IV Setup, Supplies
Discharge charges (A03):    ED Visit (99284), CBC (85025),
                             X-Ray (71046), IV Infusion, Hospital Care

8 — X12 837P & 835

837P — Professional Claim
StandardASC X12 005010X222A2
Segment sepTilde ~ (element sep: *)
ISA/GSInterchange + functional group envelope
ST*837Transaction set header
CLM01Claim ID (unique per bill)
CLM02Total billed amount
CLM05Place of service + frequency (11:B:1 = office)
LX*NService line counter (1, 2, 3…)
SV1*HC:codeCPT procedure code + charge + units
DTP*472Date of service (D8 format = YYYYMMDD)

One DFT message = one CLM loop. Each FT1 charge line = one LX/SV1 pair.

835 — Remittance Advice (ERA)
StandardASC X12 005010X221A1
PurposePayer → Provider: explanation of payment
BPRFinancial information (payment amount, ACH details)
TRNTrace number (check/EFT reference)
CLP01Claim reference number (matches 837P CLM01)
CLP02Claim status (1=paid, 2=adjusted, 3=denied)
CLP03Total billed (should match 837P CLM02)
CLP04Total paid
SVCService line detail (per CPT code)
CAS*CO*45Adjustment: contractual write-off

The 835 is how providers know what was paid for each claim. Balance = billed − paid − write-off.

9 — SFTP Flat-File Ingestion

Pipeline Steps
1. File upload  →  POST /api/sftp/upload/  (multipart)

2. Decode bytes  (UTF-8-BOM → UTF-8 → Latin-1)

3. Detect delimiter  (count commas vs pipes vs tabs in header row)

4. csv.DictReader  with detected delimiter

5. Detect schema  (header overlap with signal sets)
   PATIENT signals:  mrn, first_name, last_name, dob, date_of_birth
   CLINICAL signals: visit_date, diagnosis_code, procedure_code, visit_type

6. Validate each row (collect errors, never abort)
   PATIENT:  mrn required · first/last_name required
             dob format + not future · gender M/F/U/O
             state 2-char
   CLINICAL: mrn required · visit_date required + not future
             diagnosis_code: regex ^[A-Z][0-9A-Z]{1,6}(\.[0-9A-Z]{1,4})?$
             procedure_code: CPT ^[0-9]{4,5}[A-Z]?$ or HCPCS ^[A-Z][0-9]{4}$

7. Intra-file MRN deduplication  (seen_mrns set)

8. Persist
   PATIENT  → PatientRecord.objects.update_or_create(mrn=...)
   CLINICAL → ClinicalRecord.objects.bulk_create(...)

9. SFTPIngestRun audit record stored regardless of outcome
ParseResult Dataclass

The parser returns a ParseResult with no ORM imports — pure data transformation layer.

FieldMeaning
schema_typePATIENT / CLINICAL / UNKNOWN
delimiter_nameCOMMA / PIPE / TAB
valid_recordslist of clean dicts (ready to persist)
validation_errorslist of {rownum, field, error, raw_value}
duplicate_mrnscount of intra-file duplicates skipped
fatal_errorset on encoding/schema/empty-file errors

Design principle: Errors are collected, not raised. A single bad row never aborts the whole file. Valid rows are persisted even if 30% fail validation.

10 — LOINC Codes

What LOINC Is & Where It Appears

LOINC (Logical Observation Identifiers Names and Codes) is the universal standard for identifying clinical observations. Every result, vital sign, and document type has a LOINC code.

HL7 v2OBX-3 (observation identifier in ORU/ORM)
FHIR R4Observation.code · DiagnosticReport.code
C-CDASection codes (48765-2 Allergies, 11450-4 Problems, etc.)
Structurecode^name^LN in HL7 (LN = LOINC system)

Common codes to know:

  • 718-7 — Hemoglobin (g/dL)
  • 4548-4 — HbA1c (%)
  • 8480-6 — Systolic BP (mmHg)
  • 2160-0 — Creatinine (mg/dL)
  • 10839-9 — Troponin I (ng/mL)
  • 34133-9 — Summarization of episode (CCD)
LOINC in an HL7 ORU message
MSH|^~\&|LAB|FAC1|EHR|FAC1|20240315||ORU^R01|MSG001|P|2.3
PID|1||P-001||Smith^John||19800315|M
OBR|1||LAB001|85025^CBC WITH DIFFERENTIAL^LN|||20240315
          ──────────────────────────────────
          OBR-4: LOINC code for the panel ordered

OBX|1|NM|718-7^Hemoglobin^LN||14.2|g/dL|13.5-17.5|N|||F
         ───────────────────
         OBX-3: 718-7 is the LOINC code for Hemoglobin
         Maps to → Observation.code.coding[0].code = "718-7"
                    Observation.code.coding[0].system = "http://loinc.org"

11 — Mirth Connect

Channel Concepts
Source ConnectorWhere messages arrive (TCP/MLLP, HTTP, file, DB)
TransformerJavaScript code that runs on every message; can map, filter, route
DestinationWhere processed messages go (REST, DB, file, another channel)
channelMapKey-value store shared between transformer and destinations
msg objectAuto-parsed HL7: msg['PID']['PID.3']['PID.3.1']
MLLPMinimum Lower Layer Protocol — wraps HL7 in TCP with VT/FS/CR framing
ACKMSH acknowledgement: AA (accept), AE (error), AR (reject)
connectorMessage.getRawData() = original HL7 string
JS Transformer — what each line does
// Parse segments
var patientId = msg['PID']['PID.3']['PID.3.1'].toString();
//  └─ msg = parsed HL7 object. PID-3.1 = first component of PID field 3
//     In HL7: PID|1||P-001^^^DEMO|||Smith^John|...
//                    ↑ PID.3.1 (MRN)       ↑ PID.5.1 (last name)

// Route by trigger event
var trigEvent = msg['MSH']['MSH.9']['MSH.9.2'].toString();
if (trigEvent == 'A01' || trigEvent == 'A03') {
  channelMap.put('routeToBilling', 'true');
  // This flag is read by the Destination Filter:
  // destination 2 only fires if routeToBilling == 'true'
}

// Build payload for REST destination connector
var payload = { patient_id: patientId, raw_hl7: connectorMessage.getRawData() };
channelMap.put('jsonPayload', JSON.stringify(payload));
// In the REST Destination body template: ${channelMap.get('jsonPayload')}

// Validation
if (!patientId) {
  channelMap.put('ackCode', 'AE');  // error ACK back to sender
} else {
  channelMap.put('ackCode', 'AA');  // accept ACK
}

12 — Tracing & Data Quality

TraceLog Model
trace_idUUID assigned at ingest, propagated to every downstream record
statusRECEIVED → VALIDATED → TRANSFORMED (or FAILED)
TraceStepOne row per pipeline step; records step name + latency_ms + status
Quality flagsINCOMPLETE: empty patient_id or VALIDATION error category
DELAYED: stuck in RECEIVED/VALIDATED > 300 seconds
DQ dashboardQueries TraceLog + HL7MessageLog + ADTMessage + DFTMessage
Auto-refresh30s interval → GET /dq/metrics/ JSON API → Chart.js update
Why Tracing Matters in Interviews

Interviewers often ask: "How would you debug a message that arrived at Mirth but never appeared in the EHR?"

  1. Check the Mirth channel dashboard — did the message enter the channel? (Source queue)
  2. Check the Transformer log — did the JS throw an error? (syntax, null PID-3)
  3. Check the Destination log — did the REST POST return a non-200? (auth, schema)
  4. Query HL7MessageLog by trace_id — what was the processing_status?
  5. Check TraceStep for the last completed step and its latency_ms
  6. Look at error_category — VALIDATION vs MAPPING vs DOWNSTREAM

How to Read the Code — Learning Path
  1. Start with a model file (e.g. adt/models.py). Understand every field. Ask: what does the DB store? What are the choices?
  2. Read the generator (e.g. adt/hl7_generator.py). It has no Django imports — pure logic. Trace how the HL7 string is built segment by segment.
  3. Read the view (e.g. adt/views.py → ADTTriggerView.post()). Follow: validate → generate → persist → respond.
  4. Run a test (python manage.py test scheduling). Read each test name to understand what the code is supposed to guarantee.
  5. Hit the endpoint with curl or the UI and read the raw JSON / HL7 back. Compare to the spec tables in this guide.
  6. Trace the data: after triggering an ADT A01, query /api/adt/dft/ — the DFT and 837P should be there automatically. That end-to-end chain is the portfolio talking point.
